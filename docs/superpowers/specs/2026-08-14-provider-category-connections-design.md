# Provider 分类型连接配置设计

## 背景

当前一个 `ProviderConfig` 只保存一组 `protocol + baseUrl + apiKey`，文本、生图和视频请求共同使用这组连接。实际供应商可能为三种能力提供不同网关、密钥和协议，导致某类型的密钥被发送到错误 Host。已观察到的鉴权失败就是中转供应商密钥被发送到 OpenAI 官方 Host。

## 目标

- 文本、生图、视频分别保存完整且互不覆盖的连接配置。
- 每种模型类型可以启用不同厂商。
- 厂商可以只配置自身支持的类型。
- 请求必须按模型类型路由到对应连接，禁止跨类型回退。
- 连接测试不调用文本、图片或视频生成接口，不产生生成费用。
- 兼容现有本地数据和导入文件，并明确标记迁移配置需要重新验证。
- 上游错误不得向界面或日志回显 API Key。

## 不在范围内

- 不新增供应商账号、额度或账单管理。
- 不自动申请、轮换或撤销 API Key。
- 不为缺少标准模型列表接口的供应商实现专用发现协议。
- 不改变生成模块的业务参数和结果展示。

## 已评估方案

### 每种类型完全独立配置（采用）

文本、生图、视频分别保存上游格式、Base URL、API Key、模型列表和默认模型。隔离最彻底，可以处理三种能力来自不同网关或不同厂商的情况。

### 共用 API Key，仅拆分 URL 和模型（未采用）

字段较少，但无法支持供应商为不同能力签发不同密钥，仍可能产生鉴权错配。

### 默认连接加类型覆盖（未采用）

兼顾复用和灵活性，但继承关系不直观，用户难以确认某次请求最终使用哪组密钥和 URL。

## 数据模型

### 类型连接

```ts
type ModelCategory = 'language' | 'image' | 'video';

interface ProviderConnection {
  protocol: ProviderProtocol;
  baseUrl: string;
  apiKey: string;
  models: string[];
  selectedModel: string;
  verification?: {
    status: 'pending' | 'healthy' | 'unhealthy' | 'unverified';
    checkedAt?: number;
    latency?: number;
    error?: string;
  };
}
```

连接是否“未配置”由字段为空推导，不另存状态。某类型完全留空时不创建对应连接。

### 厂商

```ts
interface ProviderConfig {
  id: string;
  name: string;
  connections: Partial<Record<ModelCategory, ProviderConnection>>;
  savedAt?: number;
}
```

厂商只保存身份和三种可选连接，不再保存共享的 `protocol`、`baseUrl`、`apiKey`、`model`、`models`、`configuredModels`、`modelSelections`、`enabled` 或共享 `health`。

### 按类型启用

Store 使用以下状态替换单个 `activeProviderId`：

```ts
type ActiveProviderIds = Partial<Record<ModelCategory, string>>;
```

每个值必须指向包含对应类型连接的厂商。删除厂商或清空类型连接时，只清除受影响类型的启用项。

## 请求路由

所有请求入口必须显式传入模型类型：

- 文本请求使用 `language`。
- 图片生成使用 `image`。
- 视频生成使用 `video`。

`configPayload(provider, category)` 只读取 `provider.connections[category]`，并使用该连接的 `selectedModel`。连接不存在或字段不完整时，在客户端请求发出前返回可读错误。不得回退到文本连接、第一条连接或其他类型模型。

服务端仍接收扁平化的单次请求配置，但增加 `category` 字段，用于错误上下文、日志脱敏和路由验证。服务端不持久化 API Key。

## 设置界面

### 厂商编辑表单

- 表单顶部编辑厂商名称。
- 下方使用“文本 / 生图 / 视频”三个顶部标签。
- 每个标签显示状态：未配置、待验证、正常、异常或未验证。
- 切换标签时保留三个类型尚未保存的草稿数据。
- 当前标签内只显示该类型的上游格式、Base URL、API Key、模型列表、默认模型和测试状态。

### 字段校验

- 某类型全部字段为空时视为未配置，不阻止保存厂商。
- 某类型只要填写任一连接字段，保存前就必须具有上游格式、Base URL、API Key、至少一个模型和默认模型。
- 默认模型必须存在于当前类型的模型列表中。
- 修改上游格式、Base URL、API Key、模型列表或默认模型后，验证状态立即变为 `pending`。
- Base URL 保存前沿用协议对应的归一化规则，并移除已粘贴的具体端点后缀。

### 连接测试

“测试连接”只作用于当前标签：

- 根据上游格式向当前 Base URL 的模型列表接口发送鉴权请求。
- 验证响应为兼容的模型列表。
- 验证默认模型存在于响应列表。
- 不调用聊天、图片生成或视频生成接口，因此不产生生成费用。
- 成功时保存归一化 Base URL、延迟、检查时间和 `healthy` 状态。
- 鉴权、URL、响应格式或模型缺失错误保存为 `unhealthy`。
- 供应商不支持标准模型列表接口时允许手动保存，状态标为 `unverified`，不伪装成验证成功。

### 厂商列表与启用

- 厂商卡片分别显示文本、生图、视频的配置和状态摘要。
- 只为已经配置的类型显示“启用文本 / 启用生图 / 启用视频”。
- 三种类型可以分别启用不同厂商。
- 启用 `healthy` 配置直接完成。
- 启用 `pending` 或 `unverified` 配置时显示一次明确警告；用户确认后允许启用并实际请求。
- 启用 `unhealthy` 配置时也允许继续，但警告中显示最近错误和检查时间。

## 状态隔离

- 某类型测试失败只更新该连接的验证状态。
- 某类型实际请求失败不修改另外两类连接。
- 修改一类配置不清除其他类型的模型选择、健康状态或启用厂商。
- 同一厂商内三类连接可以使用完全不同的上游格式、Host 和 API Key。

## 错误与密钥安全

- 客户端错误格式包含模型类型、目标 Host、HTTP 状态码和脱敏后的上游原因。
- 示例：`生图连接 · image.example.com · 401：鉴权失败`。
- 服务端在返回错误和写入日志前清理疑似密钥片段，包括上游错误中回显的 Bearer Token、`api-key` 值和常见 Key 模式。
- 错误响应不得包含完整 Key、Key 前缀与尾部组合或请求头内容。
- 前端不得把 API Key 写入健康状态错误、通知、任务记录或浏览器日志。
- 每次请求只携带当前模型类型连接的 Key。

## 旧数据迁移

Zustand 持久化版本从 4 升级到 5。

对每个旧厂商：

1. 读取旧 `configuredModels`，并通过模型能力标签拆分为文本、生图、视频三个列表。
2. 只为具有对应能力模型的类型创建连接。
3. 将旧上游格式、Base URL 和 API Key 复制到这些连接。
4. 将旧 `modelSelections[category]` 迁移为对应连接的 `selectedModel`；缺失时使用该类型第一项模型。
5. 每个迁移连接统一标为 `pending`，要求重新验证。
6. 旧 `activeProviderId` 只迁移到该厂商实际存在连接的类型，形成 `activeProviderIds`。
7. 无能力标签的旧模型迁移到文本连接，避免丢失，但文本连接仍标为待验证。

迁移不得删除旧存储值后再分步写入；必须在单次 Zustand migrate 中原子返回版本 5 状态。

## 导入与导出

- 导出格式版本从 1 升级到 2，包含 `activeProviderIds` 和每个厂商的 `connections`。
- 导入版本 2 时校验三类连接结构和默认模型引用。
- 导入版本 1 时复用本地版本 4 到 5 的迁移规则。
- 导入后的健康状态统一改为 `pending`，不信任其他设备上的历史验证结果。
- 导出文件仍包含 API Key，下载前继续提示用户妥善保管。

## 组件与模块边界

- `useProviderStore.ts`：定义新数据结构、按类型启用状态、选择器和版本迁移。
- `providerService.ts`：提供按类型解析连接和构造请求配置的唯一入口。
- `providerGateway.ts`：执行模型列表验证、按类型补充错误上下文并脱敏上游错误。
- `ApiSettings.tsx`：管理厂商级草稿和顶部类型标签。
- `ProviderConnectionEditor`：编辑单一类型连接，不访问其他类型数据。
- 各生成与文本消费模块：只请求自身类型的启用厂商和连接。

不在多个页面重复拼装 `baseUrl + apiKey + model`；所有消费者通过 store 选择器和 provider service 获取类型连接。

## 验收标准

- 同一厂商可为三种类型保存不同协议、URL、Key 和模型。
- 厂商可以只配置任意一个或两个类型并成功保存。
- 文本、生图、视频可以分别启用不同厂商。
- 三种请求分别到达各自配置的 Host，且不发生跨类型回退。
- 修改任一连接后，该连接变为待验证，其他连接状态不变。
- 连接测试只访问模型列表接口，不触发聊天、图片或视频生成。
- 无模型列表接口的配置可以手动保存，并以未验证状态警告启用。
- 旧数据按能力拆分并保留模型和默认选择，迁移连接统一待验证。
- 版本 1 导入文件可以迁移，版本 2 可以完整往返导入导出。
- 上游错误和应用日志不包含完整或部分 API Key。

## 验证计划

- 为 store 版本 4 到 5 迁移编写单元测试，覆盖单类型、三类型、缺少能力标签和删除厂商。
- 为按类型连接选择器编写单元测试，证明不存在跨类型回退。
- 为 Provider Gateway 编写测试，覆盖三类模型列表鉴权、模型缺失、非 JSON 响应和不支持列表接口。
- 为错误脱敏编写回归测试，输入包含回显 Key 的上游错误，断言响应与日志均不包含任何 Key 片段。
- 浏览器验证顶部标签草稿保持、部分类型保存、状态变化和按类型启用。
- 使用三个不同的本地测试 Host 验证文本、生图、视频请求各自路由正确。
- 完成模块后运行 `npm run typecheck:client`、`npm run typecheck:server` 和 `npm run lint`；阶段完成后运行测试与构建。
